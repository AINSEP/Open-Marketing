- **The provider-dispatcher "dead code" pattern the brief warned about (seen on a prior repo) does not reproduce here.** Every provider directory under `packages/providers/src/lib/{email,sms,push,chat}` has a live handler registered in its channel's factory (`libs/application-generic/src/factories/{mail,sms,push,chat}/*.factory.ts`) — verified by direct count, not by file presence (§4).

## 1. What Novu is, in plain terms

Novu is a multi-channel notification engine you self-host or consume as SaaS. The pitch: instead of writing separate integration code for SendGrid, Twilio, FCM, Slack, and a WebSocket feed — plus separate logic for "don't send this five times in ten minutes" and "respect this user's opt-out" — you define a **workflow** once, trigger it with one API call, and Novu handles channel selection, provider delivery, batching, timing, and per-user preferences.

**What a user sets up:** an "Integration" per channel (an SMTP/API-key credential for a provider — SendGrid, Twilio, FCM, Slack, etc.), and one or more "Workflows." A workflow is a named sequence of **steps** — some are channel sends (email, SMS, push, chat, in-app), others are control-flow (digest, delay, throttle, custom code, an HTTP callout). Workflows can be authored two ways: through the dashboard UI (steps stored as embedded documents on a `NotificationTemplate` Mongo document, `libs/dal/src/repositories/notification-template/notification-template.schema.ts`), or in code using `@novu/framework`'s `workflow()` builder (`packages/framework/src/resources/workflow/workflow.resource.ts:32`), where the workflow's logic lives in the developer's own app and Novu calls back into it at send time via an HTTP "Bridge" endpoint (`ExecuteBridgeJob`, referenced throughout `apps/worker/src/app/workflow/usecases/execute-bridge-job/`).

**What happens when it runs:** an external caller (or the developer's own backend) POSTs to `/v1/events/trigger` with a workflow identifier, a payload, and a list of recipients (subscriber IDs, inline subscriber objects, or topic keys). Novu resolves the workflow, resolves the recipient list (expanding topics to their subscriber sets), and for every (workflow, subscriber) pair walks the step chain: evaluate per-step conditions and channel preferences, run digest/delay/throttle logic if present, and for a channel step, pick an active provider integration and call it. Every hop is recorded (`ExecutionDetails`/trace rows) so a support engineer can see exactly why a given subscriber did or didn't get a message.

**The self-service inbox angle:** Novu ships an embeddable `<Inbox />` component (`packages/react`, `packages/js`) backed by its own in-app channel — no third-party provider, just a Mongo `Message` collection plus a Socket.IO push (`apps/ws`) — so "notification center in your product" is a first-class, zero-integration channel alongside the outbound ones.

## 2. Core concepts, as the code models them

- **Subscriber** — `libs/dal/src/repositories/subscriber/subscriber.schema.ts`. A person or agent identity scoped to an environment (`_environmentId` + your own `subscriberId`), holding channel addresses (email, phone, push `deviceTokens`), locale, timezone, and arbitrary `data`. Created/updated implicitly on first trigger (`CreateOrUpdateSubscriberUseCase`, called from both `TriggerEvent` for actors and `SubscriberJobBound` for recipients).
- **Workflow** (Mongo collection name: `NotificationTemplate`) — `libs/dal/src/repositories/notification-template/notification-template.schema.ts:105-258`. Holds `triggers[]` (the identifier and expected payload/subscriber variables used to match an incoming trigger, indexed at `notification-template.schema.ts:311-314`), an ordered `steps[]` array (each step embeds its own `filters`, `metadata` for digest/delay config, and `variants` for A/B), workflow-level `preferenceSettings` (which channels are user-toggleable at all), `critical` (bypasses subscriber schedule/preference gating in places, see §7), and `severity`.
- **Step** — an element of `steps[]`, or (code-first) a call inside the `execute` function passed to `workflow()`. Has a `type` from `StepTypeEnum` (`TRIGGER, IN_APP, EMAIL, SMS, CHAT, PUSH, DIGEST, DELAY, THROTTLE, CUSTOM, HTTP_REQUEST`, referenced in `apps/worker/src/app/workflow/usecases/add-job/add-job.usecase.ts:1149-1161`). At runtime a step becomes one `Job` document (below); a `Job._parentId` chains steps into the workflow's linked-list execution order.
- **Job** — `libs/dal/src/repositories/job/job.schema.ts`. The DB-persisted unit of execution: one per (notification, step). Carries `status` (`PENDING/QUEUED/RUNNING/DELAYED/MERGED/SKIPPED/CANCELED/COMPLETED/FAILED`), `digest`/`delay` metadata, `_mergedDigestId` (set when this job's events were folded into another job's digest window), and `_parentId` for chaining. This is the row that BullMQ/SQS job IDs reference — see §3.
- **Notification** — `libs/dal/src/repositories/notification/notification.schema.ts`. One per (workflow, subscriber, trigger). Parent of all the `Job`s and `Message`s produced by that trigger for that subscriber; holds `_digestedNotificationId` when merged into another notification's digest.
- **Message** — `libs/dal/src/repositories/message/message.schema.ts`. One per actual send attempt on a channel step — the delivery record. Holds channel, provider, rendered content, `seen`/`read`/`archived`/`snoozedUntil` (in-app specific), and `deliveredAt`.
- **Topic** — `libs/dal/src/repositories/topic/topic.schema.ts`. A named fan-out list, unique per `(environmentId, key)` (`topic.schema.ts:37-45`). `TopicSubscribers` (`topic-subscribers.schema.ts`) is the join table; subscribers are added/removed independently of any trigger.
- **Tenant** — `libs/dal/src/repositories/tenant/tenant.schema.ts`. Not an isolation boundary (that's `_organizationId`/`_environmentId` on every collection) — it's a per-send "customer context" object (`identifier`, `name`, arbitrary `data`) a B2B2C sender attaches to a trigger so templates can reference "which of my customers this is for" (`SendMessage.handleTenantExecution`, `apps/worker/src/app/workflow/usecases/send-message/send-message.usecase.ts:580-609`).
- **Layout** — `libs/dal/src/repositories/layout/layout.schema.ts`. A reusable email wrapper (header/footer chrome) a step's email template can reference; resolved at send time (`GetLayoutUseCaseV0`, wired into `SendMessageEmail` at `send-message-email.usecase.ts:11,72,164`).
- **Integration** — `libs/dal/src/repositories/integration/integration.schema.ts`. A credentialed provider connection: `channel` + `providerId` + encrypted `credentials`, `active`/`primary`/`priority`/`conditions` for selection among multiple integrations on the same channel, and a `kind: 'delivery' | 'agent'` split introduced for the ACI feature (`integration.schema.ts:22-26`).

## 3. Trigger → delivery, traced end to end

Novu's execution pipeline is three chained queues (BullMQ locally, SQS in the AWS-shaped deployment — both are supported behind the same `WorkerOptions`/`BullMqService`/`SqsService` abstraction) plus a fourth for the in-app fan-out. Every hop below is a real process boundary; a message can sit queued at any of them.

1. **HTTP entry** — `POST /v1/events/trigger`, `apps/api/src/app/events/events.controller.ts:104-133`. Auth + a per-org kill-switch feature-flag check (`checkKillSwitch`, `events.controller.ts:71-83`), then delegates to `ParseEventRequest.execute` (`ParseEventRequestMulticastCommand`). Sibling endpoints: `/trigger/bulk` (`events.controller.ts:155-171`, ≤100 events/request), `/trigger/broadcast` (`events.controller.ts:195-217`, addresses every subscriber in the environment), and `DELETE /trigger/:transactionId` to cancel an in-flight digest/delay (`events.controller.ts:259-268`, → `CancelDelayed`).
2. **Parse & enqueue** — `apps/api/src/app/events/usecases/parse-event-request/parse-event-request.usecase.ts`. Validates the trigger payload against the workflow's declared JSON Schema (Ajv, `parse-event-request.usecase.ts:42-58`), applies SSRF protection to any bridge URL (`assertSafeOutboundUrl`, imported at line 6), generates a `transactionId` if the caller didn't supply one, and pushes an `IWorkflowDataDto` onto the **workflow queue** (`WorkflowQueueService`, injected at line 77). The API process does not run the workflow itself — this is a pure validate-and-enqueue tier.
3. **Workflow queue consumer** — `apps/worker/src/app/workflow/services/workflow.worker.ts`. Runs in `apps/worker`, calls `TriggerEvent.execute` (`workflow.worker.ts:27,90ish`, `TriggerEvent` from `libs/application-generic/src/usecases/trigger-event/trigger-event.usecase.ts`). `TriggerEvent` looks up the stored workflow by trigger identifier (LRU-cached, `trigger-event.usecase.ts:370-387`), merges default payload values (`VerifyPayload`, line 74-82), resolves `tenant` and `actor` (an optional "who caused this" subscriber, lines 126-175), and dispatches by addressing type to `TriggerMulticast` or `TriggerBroadcast` (lines 177-209).
4. **Recipient resolution & fan-out enqueue** — `libs/application-generic/src/usecases/trigger-multicast/trigger-multicast.usecase.ts:46-199`. Splits the `to` list into direct subscriber IDs vs. topic keys (`splitByRecipientType`, line 284). Direct subscribers go straight to the next queue. Topic keys are resolved via a cursor-based generator, `TopicSubscribersRepository.getTopicDistinctSubscribers` (line 81), batched at `SUBSCRIBER_TOPIC_DISTINCT_BATCH_SIZE` (default 100, line 25) — this streams rather than materializing the whole subscriber list, which matters for large topics. Both paths converge on `TriggerBase.sendToProcessSubscriberService` (`libs/application-generic/src/usecases/trigger-base/trigger-base.usecase.ts:74-91`), which chunks the batch (`_.chunk`, line 52) and calls `SubscriberProcessQueueService.addBulk` — the **subscriber-process queue**.
5. **Subscriber-process consumer → job-chain creation** — `apps/worker/src/app/workflow/services/subscriber-process.worker.ts:91-132` calls `SubscriberJobBound.execute` (`apps/worker/src/app/workflow/usecases/subscriber-job-bound/subscriber-job-bound.usecase.ts`). This creates/updates the subscriber, evaluates workflow-resource preferences (`GetPreferences`, imported line 10), calls `CreateNotificationJobs` to build the full ordered array of `Job` documents (one per workflow step, linked by `_parentId`) plus the parent `Notification` row, then calls `StoreSubscriberJobs.execute` (`apps/worker/src/app/workflow/usecases/store-subscriber-jobs/store-subscriber-jobs.usecase.ts:26-54`), which bulk-inserts the jobs (`jobRepository.storeJobs`, line 29) and kicks off execution by calling `AddJob.execute` for **only the first job** in the chain (lines 41-53).
6. **AddJob: gatekeeper for deferred steps** — `apps/worker/src/app/workflow/usecases/add-job/add-job.usecase.ts:108-173`. For `DIGEST`/`DELAY`/`THROTTLE` steps this runs the deferred-execution logic described in §5/§6 instead of queuing immediately. For everything else (`executeNoneDeferredJob`, lines 410-426) it marks the job `QUEUED` and calls `queueJob` (lines 1061-1097), which adds a message to the **standard queue** with `delay: 0`.
7. **Standard queue consumer → per-step execution** — `apps/worker/src/app/workflow/services/standard.worker.ts:141-199` calls `RunJob.execute` (`apps/worker/src/app/workflow/usecases/run-job/run-job.usecase.ts:84-424`). This re-fetches the job, checks whether it was canceled (a merged/skipped digest chain, lines 102-119), evaluates the subscriber's send-time schedule (`GetSubscriberSchedule` / `isWithinSchedule`, lines 176-256), then calls `SendMessage.execute`.
8. **Channel dispatch & preference gate** — `apps/worker/src/app/workflow/usecases/send-message/send-message.usecase.ts:90-213`. Runs step `filters` (`ConditionsFilter`) and channel preference (`evaluateChannelPreference`, lines 323-421 — the single enforcement point, see §7) **in parallel** (line 222), skips the step if either fails, then switches on `stepType` to one of `SendMessageEmail/Sms/InApp/Chat/Push` (lines 175-212), or back into `Digest`/`SendMessageDelay`/`Throttle` for control-flow steps.
9. **Provider call & delivery record** — e.g. `apps/worker/src/app/workflow/usecases/send-message/send-message-email.usecase.ts`. Picks an active integration (`SelectIntegration.getIntegration`, lines 94-104 — filtered by `active`, `primary`/`priority`, and `conditions` such as tenant match), writes a `Message` row up front (lines 193-213, `status` default `'sent'` per the schema), compiles the template (`CompileEmailTemplate`), then (not shown above but the same pattern in every `send-message-*` usecase) builds the provider handler via the channel's factory and calls `.send()`. Success/failure updates the `Message` and emits `ExecutionDetails`/webhook events.
10. **Chain continuation** — back in `RunJob`, the `finally` block calls `tryQueueNextJobs` (`run-job.usecase.ts:468-638`), which finds the job whose `_parentId` is the one just completed and re-enters `AddJob` — repeating from step 6 for the next step in the workflow.

In-app delivery adds a fourth queue: `send-message-in-app.usecase.ts` writes the `Message` (line 218) then pushes to `WebSocketsQueueService` (line 276); `apps/ws`'s `WebSocketWorker` (`apps/ws/src/socket/services/web-socket.worker.ts:61-103`) consumes it and calls `ExternalServicesRoute`, which reaches `WSGateway.sendMessage` (`apps/ws/src/socket/ws.gateway.ts:170-201`) to emit over the subscriber's Socket.IO room. See §8.

## 4. The provider abstraction

**Shape.** Each channel (`mail`, `sms`, `push`, `chat`) has a `*.factory.ts` in `libs/application-generic/src/factories/<channel>/` holding a flat array of handler instances and a `getHandler(integration)` method that linear-scans for the first handler whose `canHandle(providerId, channel)` matches (e.g. `libs/application-generic/src/factories/mail/mail.factory.ts:26-63`). A handler wraps one third-party SDK/HTTP client behind a small interface (`buildProvider(credentials)`, `send(...)`); the actual SDK code lives one level down in `packages/providers/src/lib/<channel>/<provider>/`.

**Provider count — verified against the dispatcher, not the file tree**, per the brief's warning about a prior repo's dead adapters:

| Channel | Provider directories | Handlers registered in the factory | Live? |
|---|---|---|---|
| Email | 20 (`packages/providers/src/lib/email/*`) | 20, all instantiated in `MailFactory.handlers` (`mail.factory.ts:27-48`) | ✅ all reachable |
| SMS | 37 (`packages/providers/src/lib/sms/*`) | 38 in `SmsFactory.handlers` (`sms.factory.ts:45-84`) — the extra one, `NovuSmsHandler`, is Novu's own built-in test provider with no separate `packages/providers` directory | ✅ all reachable |
| Push | 8 (`packages/providers/src/lib/push/*`) | 8, all instantiated (`push.factory.ts:15-24`) | ✅ all reachable |

No handler throws `not implemented`; every provider directory has a live entry in its channel's dispatch array (confirmed by exact count, not a `not-implemented` grep, which returned nothing). Total: **~79 third-party channel integrations**, all reachable from the trigger path — this is real breadth, not a facade.

**Selection.** `SelectIntegration` (used identically from every `send-message-*` usecase, e.g. `send-message-email.usecase.ts:94-104`) queries `Integration` documents for the org/environment/channel, filtered by `active: true`, ordered by `primary`/`priority`, and narrowed by `conditions` (e.g. a tenant match — `integration.schema.ts:121-137`). If no matching integration exists, `getHandler` returns `null` (mail throws; push/chat/sms return `null`) and the step fails with `SUBSCRIBER_NO_ACTIVE_INTEGRATION`.

**Credential storage.** Symmetric encryption at rest: `libs/application-generic/src/encryption/cipher.ts` — AES-256-CBC, random 16-byte IV per encryption, key from the `STORE_ENCRYPTION_KEY` env var, stored as `iv_hex:ciphertext_hex`. `GetDecryptedIntegrations` (`libs/application-generic/src/usecases/get-decrypted-integrations/get-decrypted-integrations.usecase.ts:56`) is the read-side decrypt call. Channel-specific OAuth tokens (Slack, agent connections) go through a parallel, provider-tagged scheme in `encrypt-channel-connection-auth.ts` (prefixes the ciphertext with `nvsk.` so a leaked value is self-identifying).

## 5. Digest and batching — the hardest part, and the most space

**The idea:** collapse N triggers for the same (workflow, subscriber, digest-key-value) that arrive within a time window into a single rendered message, without losing any of the underlying event payloads.

**What backs the timer.** A digest step is *not* a scheduled cron job or a Redis sorted set — it's a **BullMQ/SQS delayed message**. When a digest job is first created, `AddJob.handleDigest` (`add-job.usecase.ts:914-967`) computes the wait duration (`ComputeJobWaitDurationService.calculateDelay`, from the step's `amount`/`unit` or a bridge-computed cron/timed output) and — critically — calls `MergeOrCreateDigest.execute` *before* deciding whether to actually enqueue a timer.

**Merge logic** (`apps/worker/src/app/workflow/usecases/add-job/merge-or-create-digest.usecase.ts:150-217`):
- `isMasterDigestOrShouldMergeToExisting` (line 161) asks the DB, via `JobRepository.getExistingDelayedJobWithTheSameDigestValue` (`libs/dal/src/repositories/job/job.repository.ts:210-224`), whether a `Job` with `status: DELAYED, type: DIGEST` already exists for the same `_templateId` + `_environmentId` + `_subscriberId` + `digest.digestValue`.
  - **No match** → this job becomes the **digest master**: `markJobAsDigestMaster` sets it `DELAYED` (`job.repository.ts:194-208`) and `AddJob.queueJob` enqueues it on the standard queue with `delay = digestAmount` (`add-job.usecase.ts:1061-1097`). This is the only job that will ever fire the BullMQ timer for this window.
  - **Match found** → `processMergedDigest` (`merge-or-create-digest.usecase.ts:82-124`) marks *this* job (and cascades to any of its own child steps via `updateAllChildJobStatus`) `status: MERGED` with `_mergedDigestId` pointing at the master, and updates the parent `Notification._digestedNotificationId`. **No new timer is created** — the event rides the master's existing delay. This is what makes arbitrarily many mid-window triggers cheap: only the first one pays for a queue entry.
- **Backoff-type digests** (`isBackOffDigestType`, line 179) invert the direction: `backoffLogic` (lines 200-217) looks for any *other, already-completed* trigger for the same digest key within the backoff lookback window (`getAnotherJobTriggeredWithinBackoffTime`, `job.repository.ts:232-244`, built from `buildLookBackDigestQuery`, lines 245-260). If one exists and started earlier, this job is `SKIPPED` outright (rather than merged) — backoff digests are "don't re-notify someone who was already notified recently," not "batch everything in a fixed window."

**Race safety at the DB layer**, not just in application code: `job.schema.ts:408-443` defines a **unique partial index** — "Guard from having two master jobs for same digest key, digest value, workflow and subscriber" — on `(subscriberId, _environmentId, digest.digestValue, digest.digestKey, _templateId, status, type)`, scoped to `status: 'delayed', type: 'digest'` and dated after 2025-03-05 (a retroactive fix, per the comment). Two concurrent `AddJob` calls racing to become master will have one of them fail the unique-index insert; `computeDigestLogicBasedOnExistingDigestState` is wrapped in `@RetryOnError('MongoServerError', { maxRetries: 3 })` (line 146-149) specifically to retry through that race and re-resolve to "merge into the winner."

**What happens to events arriving mid-window:** each merged trigger's payload is preserved as its own `Job.payload` — merging only changes `status`/`_mergedDigestId`, it never deletes or overwrites the job document. So the full set of original payloads survives until render time.

**Rendering the digest.** When the master's delayed job finally fires, `RunJob` calls `SendMessage`, which for a `DIGEST` step type calls `Digest.execute` (`apps/worker/src/app/workflow/usecases/send-message/digest/digest.usecase.ts:47-102`). Behind a feature flag (`IS_USE_MERGED_DIGEST_ID_ENABLED`) there are two collection strategies:
- **Current path**, `getEvents` (lines 104-117): `jobRepository.find({ _mergedDigestId: currentJob._id, status: MERGED, type: DIGEST, _subscriberId })` — a single indexed query (the `_mergedDigestId` sparse index, `job.schema.ts:408-415`) that returns every job that merged into this master, then returns `[masterPayload, ...mergedPayloads]`.
- **Legacy path**, `backwardCompatibleGetEvents` (lines 119-133): dispatches to `GetDigestEventsRegular` or `GetDigestEventsBackoff` depending on digest type — an older, more query-heavy reconstruction kept for compatibility.

The collected `events[]` array is written onto **every downstream job in the same transaction** (`jobsToUpdate`, lines 77-91 — not just the digest job itself, so later steps like "send one email" can read `job.digest.events`), and the digest step's own job is returned with the updated payload so `RunJob` can pass `command.events` into the next `SendMessage` call (`run-job.usecase.ts:290`, `events: job.digest?.events`). The actual "batch these into one email" logic is then just template authoring — the workflow's next step (e.g. an email) receives `events`/`total_count` in its compile context (`send-message.usecase.ts:461-464`) and the template loops over them.

**Cancellation.** `DELETE /trigger/:transactionId` → `CancelDelayed` marks the matching `DELAYED` job canceled; `RunJob.delayedEventIsCanceled` (`run-job.usecase.ts:681-698`) checks for this on every fire and, if the canceled job was a digest master with mid-flight followers, promotes the oldest follower to take over as executor (`activeDigestMainFollowerExist`, lines 700-723) rather than dropping the whole batch.

## 6. Delay, throttle, and step control flow

All three non-send control steps (`DIGEST`, `DELAY`, `THROTTLE`) share the same gate: `isJobDeferredType` (`add-job.usecase.ts:1163-1167`) routes them through `executeDeferredJob` instead of immediate queuing.

- **Delay** (`add-job.usecase.ts:310-338`, `handleDelay` lines 428-471): computes a wait duration from static config or a dynamic payload-path lookup (`parseDynamicDurationValue`, lines 769-813, supports both ISO-8601 timestamps and `{amount, unit}` objects), marks the job `DELAYED`, and — like digest — relies on `queueJob`'s `delay` parameter on the standard queue to resume it later. Unlike digest, there is no merge step; a delay job always gets its own timer.
- **Throttle** (`handleThrottle`, lines 815-912): a rate limiter, not a batcher. Reserves a slot in a **Redis-backed sliding/fixed window** via `RedisThrottleService.reserveThrottleSlot` (called line 872), keyed by `(environmentId, subscriberId, workflowId, stepId, throttleKey)`. If the window's `threshold` is already met, the step and every remaining step in the chain are marked `SKIPPED` (`handleThrottleSkip`, lines 1004-1051, including cascading `updateAllChildJobStatus`) rather than queued — throttle drops the notification outright past the limit, it does not queue it for later.
- **Subscriber schedule extension**: a separate mechanism from delay/digest/throttle — if a workflow step would fire outside a subscriber's configured quiet hours, `RunJob.shouldExtendToSubscriberSchedule`/`extendJobToNextAvailableSchedule` (`run-job.usecase.ts:885-1020`) re-queues the same job for the next in-schedule time, capped at 3 extensions (`MAX_EXTENSIONS`, line 916) before it gives up and sends anyway.
- **Failure/backoff control flow**: `StandardWorker.jobHasFailed` (`standard.worker.ts:230-285`) distinguishes a webhook-filter backoff (custom `BackoffStrategiesEnum.WEBHOOK_FILTER_BACKOFF`, retried up to `DEFAULT_ATTEMPTS`) from a terminal failure; `job.step.shouldStopOnFail` (schema field, `notification-template.schema.ts:18-21`) decides whether one step's failure cancels every remaining step in the chain (`jobRepository.cancelPendingJobs`, called from both `RunJob` and `StandardWorker`).
- **Other non-send steps**: `CUSTOM` (arbitrary code, `ExecuteCodeFirstCustomStep`) and `HTTP_REQUEST` (`ExecuteHttpRequestStep`) are dispatched the same way as channel sends in `SendMessage.execute`'s switch (`send-message.usecase.ts:203-208`) but skip the deferred-job machinery — they run immediately, once, with no timer.

## 7. Subscriber preferences and opt-out

**Storage:** a single `Preferences` collection (`libs/dal/src/repositories/preferences/preferences.schema.ts`) with a `type` discriminator (`PreferencesTypeEnum`) covering **five tiers**: `WORKFLOW_RESOURCE` (the workflow author's default), `USER_WORKFLOW` (an org member's override of that default), `SUBSCRIBER_GLOBAL` (a subscriber's blanket opt-out across all workflows), `SUBSCRIBER_WORKFLOW` (a subscriber's per-workflow override), and `SUBSCRIPTION_SUBSCRIBER_WORKFLOW` (a subscriber's override scoped to one topic subscription — `preferences.schema.ts:195-214`). Each row stores per-channel `enabled` flags plus an `all.enabled`/`all.readOnly` master switch and an optional `schedule`.

**Resolution order is a single, explicit function** — `MergePreferences.execute` (`libs/application-generic/src/usecases/merge-preferences/merge-preferences.usecase.ts:58-98`), with the precedence spelled out in its own docstring (lines 12-17): **workflow resource → workflow user → subscriber global → subscriber workflow**, later entries overriding earlier ones via a deep merge (`toMerged`). Two carve-outs are enforced in the same function: if any workflow-level preference has `all.readOnly: true`, or the caller passed `excludeSubscriberPreferences`, subscriber tiers are dropped from the merge entirely (lines 67-73) — i.e. the workflow author can make a channel non-optional.

**Enforcement is centralized, not scattered.** There is exactly one call site that gates an actual send: `SendMessage.evaluateChannelPreference` (`apps/worker/src/app/workflow/usecases/send-message/send-message.usecase.ts:323-421`), invoked from `SendMessage.execute` (line 119, in parallel with step-condition filtering) before the switch that dispatches to a channel usecase. It only applies to the five channel-shaped step types (`isChannelStep`, lines 552-556: `IN_APP, EMAIL, SMS, PUSH, CHAT`); `HTTP_REQUEST`/`CUSTOM`/control-flow steps are not preference-gated. `stepPreferred` (lines 541-550) requires both `preference.enabled` (the workflow-level gate) and the specific channel's flag. A skip records *which tier* caused it via `preferenceDetailFromPreferenceType` (lines 384-392), so execution-detail traces distinguish "blocked by workflow default" from "blocked by subscriber's own opt-out" — useful for support/debugging, and evidence the precedence chain is actually exercised in production rather than merely modeled.

**Stateless workflows** (code-first, no DB-stored `NotificationTemplate`) skip the DB lookup and instead have their default preferences carried inline on the trigger command (`command.statelessPreferences`, lines 346-360) — same merge function, same enforcement point, different preference source.

## 8. In-app / websocket delivery

In-app is architecturally the odd channel out: it has no third-party provider, no `packages/providers` entry, and no encrypted credentials — the "provider" is Novu's own database and socket server.

- **Write path**: `SendMessageInApp` creates a `Message` row directly (`send-message-in-app.usecase.ts:218`, with in-app-specific fields `seen`, `read`, `archived`, `snoozedUntil` on the schema, `message.schema.ts:77-97`), then enqueues a **separate** `WebSocketsQueueService` job (line 276) rather than calling the socket server synchronously — a deliberate decoupling so a slow or down `apps/ws` instance never blocks the notification pipeline.
- **Fan-out**: `apps/ws`'s `WebSocketWorker` (`web-socket.worker.ts:61-103`) is explicitly documented as **at-most-once**: its SQS failed-handler always returns `false` (drops, never retries) with the rationale, in the code comment, that "WS payloads are point-in-time UI hints... replaying them after the visibility timeout is harmful" (lines 34-43). This is a real design choice, not an oversight — in-app "new message" pushes are a live-UI nicety, and the client's REST-backed unread-count poll is the durable source of truth.
- **Socket layer**: Socket.IO (`apps/ws/src/socket/ws.gateway.ts`), JWT-authenticated on connect (`getSubscriber`, lines 79-92, audience must be `widget_user`), one room per subscriber's internal `_id` (`connection.join(subscriber._id)`, line 159). `sendMessage` (lines 170-201) additionally filters by **context keys** — an exact-match comparison (`isExactMatch`, lines 203-214) between the message's context and the specific socket's subscribed context, letting one subscriber run multiple differently-scoped inbox widgets (e.g. per-workspace) over the same connection set. Disconnect/reconnect updates an online-presence flag (`SubscriberOnlineService`) independent of message delivery.
- **Unread/unseen counts** are computed on demand per-socket (`sendUnreadCountToAllConnections`/`sendUnseenCountToAllConnections`, lines 216-333) directly from `MessageRepository` counts, including a severity breakdown — this is a read-side aggregation, not a maintained counter column.

## 9. Topics and tenants

**Topics** are the fan-out primitive (§3, step 4): a `(environmentId, key)`-unique named list (`topic.schema.ts:37-45`) with a separate `TopicSubscribers` join collection. Triggering "to a topic" is resolved via a streaming cursor (`getTopicDistinctSubscribers`) rather than loading the full member list into memory, and per-recipient exclusions (`ITopic.exclude`) are applied before the DB scan (`trigger-multicast.usecase.ts:67-69, 284-321`) so an excluded subscriber never round-trips through the topic query. A subscriber can belong to many topics, and a trigger can target several topics plus explicit subscriber IDs in the same call — deduplicated into one subscriber map before fan-out (lines 92-146).

**Tenants** are not a security/isolation boundary in this codebase — that role belongs entirely to `_organizationId`/`_environmentId`, present on every collection and every query shown in this document. A `Tenant` is a per-send context object a B2B2C sender attaches so templates can render "this is about customer X" (`handleTenantExecution`, `send-message.usecase.ts:580-609`) and so an `Integration`'s `conditions` can route a specific tenant to a specific provider account (`integration.schema.ts:121-137`). If a referenced tenant identifier doesn't exist, the step continues (with a `TENANT_NOT_FOUND` execution-detail trace) rather than failing the whole workflow.

## 10. Data model

MongoDB via Mongoose throughout (`libs/dal/src/repositories/**`). Every collection carries `_environmentId`/`_organizationId` and most are indexed on them first — that pairing is the real multi-tenancy boundary (§9). Key collections:

| Collection | Key fields | What the indexes reveal |
|---|---|---|
| `NotificationTemplate` (workflow) | `triggers[].identifier`, embedded `steps[]` (each with `filters`, `metadata`, `variants`) | Indexed on `(environmentId, triggers.identifier)` (`notification-template.schema.ts:311-314`) — workflow lookup by trigger name is the hot path, matching §3 step 3's cache-then-index pattern |
| `Job` | `status`, `type`, `_parentId`, `digest.{digestValue,digestKey}`, `_mergedDigestId` | Six purpose-built indexes, each with an inline comment naming the exact query it serves (`job.schema.ts:192-420`) — including the digest-race-safety unique partial index (§5) and a plain `createdAt` index annotated "created to push entries to Online Archive" (line 420), i.e. Mongo's tiered-storage feature is in active use for job history |
| `Notification` | `_templateId`, `_subscriberId`, `_digestedNotificationId` | Parent of a trigger's job/message tree; digest merges point here too, not just on `Job` |
| `Message` | `channel`, `providerId`, `seen/read/archived/snoozedUntil`, `channelData[]` (per-channel device/session tokens) | Five overlapping compound indexes on `(_subscriberId, _environmentId, channel, ...)` (`message.schema.ts:257-389`) — this collection is read far more than written (inbox list queries dominate), and `contextKeys` is indexed (line 261) confirming the multi-context inbox from §8 is a first-class query shape, not an afterthought |
| `Subscriber` | `subscriberId`, channel addresses, `data`, `timezone` | — |
| `Preferences` | `type` (5-way discriminator), `contextKeysHash` (a SHA-256 of sorted context keys, computed in a `pre('save')` hook, `preferences.schema.ts:106-122`) | Four separate unique partial indexes, one per preference tier that needs one-row-per-scope uniqueness (`preferences.schema.ts:139-214`) — the `contextKeysHash` trick lets "one preference per subscriber per context" be enforced by a plain unique index instead of an array-equality query |
| `Topic` / `TopicSubscribers` | `key` (unique per env), subscriber↔topic join | — |
| `Tenant` | `identifier`, `data` | Indexed on `(_environmentId, createdAt)` for paginated tenant listing only — no uniqueness constraint on `identifier` beyond the query layer |
| `Integration` | `channel`, `providerId`, `credentials` (encrypted), `active/primary/priority/conditions`, `kind` | A partial unique index scoped to `providerId: NovuAgent` (lines 164-173) for the ACI shared-inbox feature — evidence the ACI feature's schema needs were bolted onto this collection rather than getting their own |

## 12. What's worth taking

Ranked by leverage for a Next.js/Electron marketing codebase; "copy closely" means the mechanism is worth porting near-verbatim, "adapt" means take the idea and rebuild it in your own stack's idioms, "skip" means not worth the integration cost here.

1. **Copy closely — the digest merge-not-reschedule pattern (§5).** The core insight — the *first* event in a window becomes a DB row with a real queue timer, every subsequent event just flips a status field and points at that row, and a DB-level unique partial index (not application logic alone) prevents two concurrent "first events" from both becoming masters — is a small, self-contained, high-value piece of distributed-systems design. It solves "batch bursty events without a scheduler poll loop or an in-memory window" using primitives (a delayed queue job + a unique index) that translate directly to Postgres + any job queue (pg-boss, BullMQ, Cloud Tasks). This is the single most reusable idea in the repo.
2. **Copy closely — the provider-factory dispatch pattern (§4).** A tiny `canHandle(providerId, channel) → handler` array with one handler class per provider, each wrapping exactly one third-party SDK behind `buildProvider`/`send`. Trivial to extend (add a file, add one line to the array), trivial to test in isolation, and the ~79-provider count here is direct evidence it scales to "every provider anyone will ever ask for" without the factory itself growing in complexity. Worth adopting verbatim for any multi-provider integration surface (email/SMS/push, but equally applicable to e.g. multiple analytics or ad-platform connectors).
3. **Adapt — the four-tier preference model with one merge function (§7).** Not the exact five `PreferencesTypeEnum` values, but the shape: default (resource) → org override (user) → subscriber blanket opt-out (global) → subscriber per-item override (workflow/subscription), collapsed through one pure function with an explicit precedence order in its docstring, called from exactly one enforcement site. This is a clean answer to "where do I put the opt-out check" that avoids the common failure mode of preference logic leaking into every send path.
4. **Adapt — execution-detail tracing as a first-class citizen.** Nearly every branch in `AddJob`/`RunJob`/`SendMessage` writes a `CreateExecutionDetails` row with a specific `DetailEnum` explaining *why* something happened (skipped by preference vs. by condition vs. by schedule vs. by throttle). This is what makes the pipeline debuggable in production without reading logs, and it's cheap to retrofit into any async pipeline: define an enum of "reasons," write one row per meaningful decision.
5. **Adapt — the queue-per-fan-out-stage decomposition (§3).** Splitting "validate & enqueue" (API) / "resolve recipients" (workflow queue) / "per-recipient job creation" (subscriber-process queue) / "per-step execution" (standard queue) into separate consumers means a slow step (e.g. a flaky email provider) never backs up recipient resolution for other workflows, and each stage can be scaled independently. Worth the queue-count overhead for any system that does fan-out-then-per-item-processing at nontrivial volume; overkill for a low-volume marketing tool.
6. **Skip — the code-first `@novu/framework` Bridge model.** Clever (workflow logic lives in the developer's own deployed app; Novu calls back via HTTP at send time), but it's a significant amount of machinery (schema transforms, a discovery protocol, SSRF-hardened outbound calls) to solve a problem — "let developers define workflows in code" — that a simpler config-as-code approach (a TypeScript file imported directly into the same process, no HTTP round-trip) solves with far less surface area for a codebase that isn't trying to be a hosted multi-tenant platform.
7. **Skip — the Socket.IO in-app channel as built.** The at-most-once, drop-on-failure WS design (§8) is a real observation, but it's this specific product's answer to a hosted-inbox-widget problem: real-time push for feature parity in a moment. For a project that isn't offering an embeddable third-party inbox component, a REST poll or a simpler SSE stream gets 90% of the value with none of the JWT-widget-auth/room/context-key machinery.
8. **Skip — the enterprise tier entirely, for a different reason than usual.** Not a licensing judgment call — the code is not in this clone to evaluate (§11). Nothing to port even if wanted.
