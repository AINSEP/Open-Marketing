1.
The `hybrid_search.sql` implementation integrates `pgvector` for semantic similarity, `pg_trgm` for lexical matching, and `PostGIS` for geospatial constraints to query the `safety_incidents` table. The core mechanism leverages Reciprocal Rank Fusion (RRF) within a PostgreSQL CTE to merge three distinct scoring functions. The `<->` operator calculates L2 distance against the `incident_embedding` column (a 1536-dimensional `vector` generated via `text-embedding-3-small`), while `ts_rank_cd` evaluates lexical relevance using a `tsvector` index on the `incident_description` column. Simultaneously, `ST_DWithin(incident_location, ST_MakePoint(longitude, latitude)::geography, search_radius_meters)` filters candidate rows before RRF aggregation. To prevent the `pgvector` HNSW index from scanning out-of-bounds geographic data, the `safety_incidents` table partitions by `ST_Geohash(incident_location, 5)` to enforce query-time partition pruning. The final output of `hybrid_search.sql` yields a normalized `rrf_score` mapping directly to the `IncidentFeedItem` component on the `SearchMapScreen`. Tuning the RRF constants heavily weights the PostGIS proximity score over the `pgvector` distance for queries explicitly mentioning street names like '3rd street', ensuring the `SafetyMapPin` UI elements cluster accurately around the viewport bounding box.

The query execution plan for `hybrid_search.sql` dictates a strict filtering sequence, preferring the `PostGIS` GiST index on `incident_location` as the innermost loop before evaluating the `pgvector` HNSW index. Wrapping the `ST_DWithin` clause in a materialized CTE named `local_incidents` limits vector distance calculations to a bounded geographical subset, sidestepping full table scans across the `safety_incidents` relation. The lexical component utilizes a `GIN` index on `to_tsvector('english', title || ' ' || description)`, which `hybrid_search.sql` queries using `websearch_to_tsquery`. When a user types 'safety on 3rd street' into the `SearchMapHeader`, the backend parses '3rd street' via the AWS Location Service integration, converts it to a `geometry(Point, 4326)`, and passes the resulting coordinate pair to the `ST_DWithin` predicate. The remaining token 'safety' feeds both the `websearch_to_tsquery` lexical match and the OpenAI embedding API. The RRF calculation normalizes the `ts_rank` and vector cosine distance (`<=>`), multiplying the `PostGIS` distance by a decay factor to produce the final `feed_ranking_score`. This orchestration ensures the `SearchResultsList` renders within the 200ms latency budget demanded by the 2025-11-28 reference architecture.

2.
The `safety_incidents` table anchors the PostgreSQL 16 schema, utilizing the `postgis` and `vector` extensions to support geographic and semantic workloads. The table definition includes an `incident_id` UUID primary key, a `reported_at` TIMESTAMPTZ column, and an `incident_location` column typed as `geography(Point, 4326)` to guarantee accurate distance calculations across the Earth's curvature. To support the 2025-11-28 UI reference featuring categorized safety reports, the schema implements an `incident_category` ENUM ('hazard', 'crime', 'infrastructure', 'community') and a `severity_level` SMALLINT. The text payloads reside in `raw_description` TEXT and `title` VARCHAR(255), which a trigger automatically concatenates and normalizes into a `search_tokens` TSVECTOR column upon INSERT or UPDATE. The `incident_embedding` column holds a `vector(1536)` datatype, populated asynchronously by the `EmbeddingWorker` Sidekiq job. To enforce spatial clustering efficiency, the table employs a BRIN index on the `reported_at` column alongside a GiST index on the `incident_location` geography column.

The schema introduces a `user_location_subscriptions` table to manage background notification mechanics for saved geographic areas. This table contains a `subscription_polygon` column typed as `geometry(Polygon, 4326)` representing the user's drawn geofence from the `SavedAreaDrawScreen`. When the `SafetyIngestionService` inserts a new row into `safety_incidents`, a Postgres LISTEN/NOTIFY channel named `new_incident_spatial_channel` broadcasts the `incident_id` and `ST_AsGeoJSON(incident_location)`. The external Node.js `SpatialSubscriptionWorker` consumes this channel, executing an `ST_Intersects` query joining the new incident's point against the `user_location_subscriptions.subscription_polygon` multipolygons. The matching `device_tokens` extract from the joined `user_devices` table and dispatch to Firebase Cloud Messaging (FCM). This schema design couples the PostGIS geometry engine directly to the asynchronous push notification pipeline, delivering alerts when a 'hazard' category event intersects the `subscription_polygon`.

3.
The incident ingestion pipeline begins at the `ReportSafetyIncidentScreen`, where the React Native client POSTs a multipart/form-data payload to the `/api/v1/incidents/ingest` endpoint on the Express.js API gateway. The `IncidentIngestionController` validates the `latitude` and `longitude` floats via Zod, discarding coordinates outside valid WGS84 boundaries, before pushing the payload into the `raw_incidents_topic` Kafka topic. The `VectorEmbeddingConsumer`, a Go-based microservice, tails this Kafka topic, buffering incoming safety reports into chunks of 50 to optimize network egress to the `text-embedding-3-small` OpenAI endpoint. The Go service extracts the `title` and `raw_description` fields, sanitizes HTML tags using the `bluemonday` package, and batches the HTTP requests to the OpenAI API. Upon receiving the 1536-dimensional float arrays, the `VectorEmbeddingConsumer` marshals the vectors into binary format and executes a bulk `COPY` command via the `pgx` driver into the `safety_incidents` table.

To handle transient failures during the embedding generation phase, the `VectorEmbeddingConsumer` leverages an exponential backoff retry mechanism utilizing the `github.com/cenkalti/backoff/v4` package. If the OpenAI API returns a 429 Too Many Requests status, the consumer pauses the Kafka partition fetcher, committing offsets only for successfully embedded records. For records lacking coordinate data, such as a user typing '3rd street' without granting device location permissions, the Go service invokes the Mapbox Geocoding API (`mapbox.places`) to reverse-geocode the text string into a WGS84 bounding box. The resulting `bbox` array transforms into an `ST_MakeEnvelope` polygon and populates an auxiliary `approximate_incident_bounds` column. This dual-pipeline ingestion strategy routes both high-precision GPS reports from the `MapPinDrop` component and low-precision textual location reports through the embedding pipeline to materialize correctly inside the `hybrid_search.sql` CTEs.

The `MapboxGL.MapView` component occupies the background `View`, dynamically loading vector tiles from the `mapbox://styles/mapbox/dark-v11` style URL. Overlaying the map, the `SafetyMapPin` component renders Custom MarkerViews, dynamically scaling `borderRadius` and `backgroundColor` based on the `severity_level` extracted from the `incident_category` GraphQL fragment. The search input lives within the `MapFloatingSearchBar` component, which manages local state via a debounced `onChangeText` handler configured to 300ms using `lodash.debounce`. Upon firing, this handler dispatches a Redux Toolkit `fetchHybridSearchResults` thunk, appending the current `region.longitude` and `region.latitude` from the `react-native-maps` `onRegionChangeComplete` callback to the query payload.

Below the map viewport, the `BottomSheetSearchResults` component from `@gorhom/bottom-sheet` houses the `RecyclerListView` displaying text-heavy incident details. Each `IncidentFeedCard` within the list relies on the `FlashList` package by Shopify to guarantee 60fps scrolling performance alongside heavy image assets and complex Flexbox layouts. The card header renders the `distance_meters` output from the PostGIS `ST_Distance` calculation, formatted via `date-fns/formatDistanceToNow` for temporal context. When a user taps an `IncidentFeedCard`, the `react-navigation/native` `Stack.Navigator` pushes the `IncidentDetailScreen`, simultaneously triggering a `MapboxGL.Camera.flyTo` animation to center the geographic point at a 16.0 zoom level. This UI architecture binds the spatial interactions of the cartography layer directly to the asynchronous data fetching lifecycle of the Apollo GraphQL client, providing visual continuity between the lexical search string 'safety on 3rd street' and the geospatial rendering of the PostGIS coordinates.

5.
The GraphQL API surface exposes the `hybridSearchIncidents` Query, resolving semantic, lexical, and geospatial parameters into parameterized `hybrid_search.sql` executions. The `IncidentResolver.ts` file utilizes Apollo Server running on Node.js, authenticating requests via a JWT parsed from the `Authorization` header using `jsonwebtoken` and validated against the `users` table via Prisma ORM. Because Prisma lacks native support for complex PostGIS and pgvector RRF queries, the resolver executes raw parameterized SQL via `$queryRawUnsafe`. The resolver accepts a `HybridSearchInput` object containing `queryString` (String), `searchRadius` (Int), `centerLon` (Float), and `centerLat` (Float). Before executing the SQL, the `EmbeddingService.ts` fetches the query vector by calling the OpenAI API with the `queryString`, mapping the returned float array into a formatted Postgres vector string `[0.123, -0.456, ...]`.

To prevent SQL injection within the raw CTE string, the resolver strictly type-casts variables, mapping `centerLon` and `centerLat` into `$1::float` and `$2::float` parameters within the `ST_MakePoint` function. The `hybridSearchIncidents` resolver implements cursor-based pagination to support the `FlashList` infinite scrolling on the mobile client. It appends a `WHERE rrf_score < $cursor` clause to the `hybrid_search.sql` output and a `LIMIT 20` constraint. The resulting rowset maps into the `SafetyIncidentEdge` GraphQL type, serializing the PostGIS `geography` binary output into a GeoJSON `Point` scalar using the `wkx` library. This resolver topology isolates heavy PostGIS computations and OpenAI network requests behind a unified GraphQL query, allowing the React Native client to fetch semantic scores, distances, and lexical matches in a single network round-trip.

6.
Caching the output of `hybrid_search.sql` requires a multi-tiered Redis architecture to handle distinct invalidation lifecycles of vector embeddings versus spatial bounding boxes. The primary caching layer employs Redis Geospatial commands (`GEOADD`, `GEORADIUS`) inside an ElastiCache cluster to index the `incident_id` and coordinates of all safety events reported within the last 24 hours. When the `MapboxGL.MapView` triggers an `onRegionChangeComplete` event without a text query, the Express API bypasses PostgreSQL entirely, issuing a `GEORADIUS` command to fetch the localized `incident_id` list, followed by an `MGET` to retrieve JSON-serialized `IncidentFeedCard` payloads. This Redis spatial index reduces PostGIS `ST_DWithin` evaluations for exploratory map panning where semantic and lexical routing remain uninvoked.

For queries invoking the full `hybrid_search.sql` pipeline, the architecture implements a semantic caching layer utilizing Redis and the `redis-om` Node package. The `SemanticCacheService` hashes the user's text query string using SHA-256 and concatenates it with a discretized Geohash of their viewport center (e.g., `semantic:9q8yy:a1b2c3d4`). The resulting payload, containing the ordered list of `incident_id`s outputted by the Reciprocal Rank Fusion, enters ElastiCache with a 15-minute TTL (`EX 900`). To prevent cache stampedes during highly localized events, the `CacheInvalidationWorker` listens to the Postgres `new_incident_spatial_channel`. When a new event arrives, the worker calculates its Geohash and executes a Redis `SCAN` command matching `semantic:<geohash>:*`, actively `DEL`eting any cached hybrid search results overlapping with the new incident's spatial domain. This pipeline pushes newly reported safety hazards into the `SearchResultsList` immediately without waiting for the 15-minute TTL expiration.

7.
During a localized safety incident, write throughput to the `/api/v1/incidents/ingest` endpoint spikes, threatening to overwhelm PostGIS index maintenance and `pgvector` HNSW graph updates. To isolate the primary read replica serving the `SearchMapScreen`, the architecture routes all `INSERT` commands to a dedicated Amazon Aurora PostgreSQL writer instance. The `RawIncidentReceiver` Lambda function intercepts POST payloads from the React Native client, pushing them directly into an Amazon SQS FIFO queue named `incident_ingestion_fifo.fifo`, decoupling the client HTTP request from the PostgreSQL transaction lifecycle. The React Native app receives an HTTP 202 Accepted status with a `pending_incident_id`, which the `PendingIncidentState` Redux slice uses to render an optimistic `SafetyMapPin` with a 0.5 opacity rendering state.

The `AuroraWriteWorker` ECS Fargate task polls the SQS queue, batching up to 100 incident payloads per transaction. Before executing the `COPY` command, the worker disables `safety_incidents` triggers and drops the `pg_trgm` GIN index temporarily if the queue depth exceeds 5,000 messages, relying on the `pg_cron` extension to rebuild text indexes during off-peak hours. The `pgvector` HNSW index configuration forces `m = 16` and `ef_construction = 64` parameters to balance graph insertion speed with recall accuracy during these bulk ingestions. Once the Aurora writer commits the transaction, the `ST_Geohash` partitions automatically route rows to their respective geographic table segments. The logical replication slot streams WAL logs to the Aurora read replicas, whereupon the GraphQL subscriptions push the finalized `incident_id` to the Apollo Client via WebSockets, transitioning the optimistic UI pin to full opacity on the user's `MapboxGL.MapView`.
